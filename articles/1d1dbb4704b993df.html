TL;DR

We serve Meta’s Muse Spark Open, an 816B-parameter mixture-of-experts model, on a single TPU v7 host of four chips, with SGLang running on the TorchTPU PyTorch backend. At the center is a megakernel: all 62 layers of a decode or verify step run as one Pallas program, and every weight load, KV read and cross-device transfer is pipelined behind compute. The rest of the work falls into three groups: faster decode steps (collective folding, a max-free attention loop that pipelines its KV chunks, an expert loop that keeps register spills off its common path, and DFlash2 speculative decoding), more KV cache per chip (sequence-on-lane KV layout in the megakernel, and L2 HiCache on TPU with session-aware eviction), and faster prefill (a fused MoE kernel and sequence parallelism).

  • The megakernel halves the time per output token for one or two concurrent requests, where it helps the most; the gain narrows as concurrency grows. Its verify step runs within 1.5–1.7× of the time it takes just to stream its weights from HBM.Decode speed.
  • On the 1M-context version of SemiAnalysis’s agentic-coding benchmark, our curve runs from 433 output tokens/s per request at 6,101 tokens/s per chip to 25,906 tokens/s per chip at 95 tokens/s per request (Figure 1).AgentX.

Background

The model

Muse Spark Open is Meta’s open-weights mixture-of-experts (MoE) [1] model, with 816B parameters in total and about 42B active per token.

  • Each layer routes every token to 8 of 256 experts.62 decoder layers, all of them MoE.
  • 46 layers use sliding-window attention [2] over the last 2,048 tokens; the other 16 attend over the full context, up to 1M tokens. Attention has 128 query heads and 16 KV heads, each 64 wide.Hybrid attention.
  • Expert weights are 4-bit, with one scale per 16 values, a microscaling format [3].NVFP4 experts.

The hardware

One host has four chips. Each chip packs two chiplets, each with one TensorCore and its own HBM, and frameworks expose each chiplet as a device, so a host has 8 devices. We shard the model 8 ways with tensor parallelism [4], one shard per device.TPU v7 (Ironwood)

1. A megakernel

At small batch, generating a token does little math per weight, so the step is as fast as HBM can stream the weights, as long as nothing interrupts the stream. A decode or verify step should therefore be one uninterrupted stream of weights from HBM into the MXU. Our previous path (“native” below) ran each layer as several kernels plus collectives, and every boundary stopped the stream. The megakernel runs all 62 layers of a step as one Pallas program per device, so the next weights are always in flight. Whole-step megakernels have been built for GPUs [8, 9] and, on TPU v7, for Kimi K3 and Qwen 3.8 [10]. Ours runs inside SGLang’s serving path, on its paged KV cache, for the decode and DFlash2 verify steps of many requests at once.

The native path was already built from fused Pallas blocks, yet its verify step took 2.9× the time needed to stream its weights. Profiling our first one-kernel prototype showed why: at batch 1 the matmuls and attention cost almost nothing, while collectives cost about 45 µs per layer. Nothing overlaps across a program boundary, so the step was bound by overhead, not by bandwidth.

Per output token, the megakernel is 1.94× faster than the native path for a single request (1.95 ms against 3.78 ms) and 1.85× for two concurrent requests. The next sections show what made one program this fast.

2. Pipelining everything inside the megakernel

A step is mostly data movement: weights, KV cache and partial sums between devices. Once the whole step is one program, the kernel can schedule every transfer so that it lands just before the compute that needs it [11], including across layer boundaries [10]. Figure 5 sketches one layer.

One layer of a step, schematic. Each DMA stream runs ahead of, or alongside, the compute that consumes it.Figure 5.

Weights arrive before they are needed

  • Attention, o-proj and router weights stream through a ring of tiles that prefetches across layer boundaries. About ten tiles in flight sustain 3.34 TB/s per device, while a single DMA stream reaches only 1.13 TB/s.A ring for dense weights.
  • The router’s choice is known only mid-layer, so the kernel requests each chosen expert’s weights the moment routing ends, with three experts in flight.Experts as soon as routing finishes.
  • Refills for the next layer’s attention weights are held until the expert loop runs, so they never compete with the expert weights the current layer is waiting for.The next layer during the expert loop.

Collectives leave as soon as their data exists

Tensor parallelism exchanges partial sums between the 8 devices several times per layer. Instead of a separate collective after each matmul, the kernel writes partial results straight into the owning device’s memory with remote DMAs issued from inside the kernel; a small round costs about 3 µs.

  • Each o-proj output tile leaves for its owner as soon as it is computed, while the next tile is still being multiplied.Streamed o-proj.

Pipelined KV writes

Each step writes its new K and V rows into the cache. In our fp8 sequence-on-lane cache (section 7), a token is one lane column of a 256-token page, so writing a token means reading the whole page block into VMEM, merging the new columns, and writing the page back.

This runs as a small kernel right after the megakernel, because XLA copies the aliased operands of any kernel that issues remote DMA. It used to do every page in turn: read, wait, merge, write, wait, for each request and each of 62 layers.

Schematic. The pipelined kernel issues all of a layer’s page reads at once, merges each page as it lands, and starts its write; the next layer’s reads start immediately on a second VMEM bank.Figure 6.

The new kernel loads all layers’ new rows once, then keeps two VMEM banks: layer l reads into one while layer l−1’s writes drain from the other, and a bank is reused only after the writes of two layers earlier have landed. The write cost per step fell from 810 to 155 µs at 16 rows and from 2,286 to 336 µs at 64 rows, with bit-identical results.

3. Collective folding

Because each layer is split across 8 devices, a device often has to collect the others’ results before it can continue. After the MoE and after attention, each device holds one slice of the layer’s output along the hidden dimension, and must all-gather the other seven slices before the next matvec can run. Collective folding lets that matvec start on the slices as they arrive instead of waiting for the whole gather, as decomposed collective matmuls do [12], here across the RMS norm that sits between the two.

Schematic. The folded matvec multiplies each gathered slice as soon as it lands, starting with the device’s own, and applies the per-row normalization at the end.Figure 7.

What makes this possible is where Muse Spark normalizes. The next layer’s attention input is an RMS norm [13] of the residual stream α·x + β·s·f, where x is the residual this device already holds, f is the gathered MoE output and s is f’s own norm factor. The two norm factors, s and the final r, are each one scalar per row. Scalars per row commute with the matmul, so the projection splits into a part the device can compute right away and a part that adds up slice by slice:

Here g is the norm’s gain vector, f_d is the slice from device d, and W_d is the matching block of weight rows. The kernel stacks the local part and the arriving slice into one product per block, consumes the slices in a fixed peer order, and reorders the weight ring so that W’s blocks stream in the same order. Once the last slice is in, it computes s and r and scales the result.

The kernel folds two all-gathers per layer this way: the MoE output into the next layer’s qkv projection, and the attention output into the pooler and router. The residual stream itself is unchanged; only the point where the matmul input is rounded to bf16 moves, so results are not bit-identical, and our accuracy checks cover it.

4. Enabling better pipelining in attention

At long context, attention is the largest part of a step. The kernel walks the KV cache chunk by chunk, and the key bottleneck was the running max of online softmax [14]: it chained every chunk to the one before, so chunks could not be pipelined.

The running max chains every chunk

Online softmax, as used by FlashAttention [15], keeps the maximum score seen so far. Each new chunk computes its scores, updates that maximum, exponentiates against it, and rescales everything accumulated so far whenever the maximum grows. So each chunk is a serial chain (wait for its DMA, QK, max, exp, sum, P·V, rescale) that cannot start its exponentials until the previous chunk’s maximum is known. In a microbenchmark this chain costs about 0.17 µs per chunk, whether the chunk is fp8 or bf16.

Muse Spark makes the max unnecessary

Muse Spark normalizes q and k (QK-norm [16, 17]) with an RMS norm that has no learned weight, and gives q a fixed gain. No attention score can exceed 43.8 in magnitude, far from where exp overflows in f32. The running max exists only to prevent that overflow, so the kernel drops it, along with the rescale. It checks the bound from the model’s constants when it is built. FlashDecoding++ [18] breaks the same chain on GPUs with a unified max value and a recomputation path for the rare overflow; here the bound is exact, so the kernel needs no fallback.

Schematic. With a running max, each chunk’s chain waits on the previous chunk. Without it, chunks are independent and their stages overlap.Figure 8.

Independent chunks pipeline

Without the max, chunks no longer depend on each other. The kernel issues all DMA waits at the top of each loop iteration, splits the chunks across several independent softmax streams that merge at the end, as Flash-Decoding does across the KV sequence [19], and software-pipelines the loop [11]: it scores the next chunks while it multiplies the previous chunks’ probabilities by V.

Three smaller changes shorten each chain further:

  • Global layers read the cache in long chunks of 1,024 to 2,048 tokens, so a 100K context needs far fewer chains. Sliding-window layers use 512-token chunks, since their window spans only a few.Chunk size by layer type.
  • Widening each fp8 chunk to bf16 on the vector unit cost more vector work than the MXU work it fed. Mixed bf16 × fp8 dots are exact, so the keys now go in as fp8.fp8 keys straight into the MXU.
  • Muse Spark’s attention scale is 1/8, a power of two, so multiplying the queries once instead of every score is exact.The attention scale in the queries.

Microbenchmark at production shapes. The memory floor is the time to read the KV bytes.Figure 9.

In the microbenchmark, longer chunks with independent streams cut attention time 2.4×, and dropping the running max took it to 3.9×. In the server, the pipelined loop raised per-request decode speed by 18% for two requests at 500K context.

5. Keeping register pressure off the common path

A processor computes on values held in its registers, a small, fixed set of storage slots next to the arithmetic units. When code needs more live values than the registers hold, the compiler spills some of them to memory and loads them back later [20], and those extra stores and loads cost time on every pass through the code. In a loop with several branches, the compiler has to fit the live values of all branches into the same registers, so one heavy branch can make every pass through the loop spill, even when that branch never runs.

The megakernel’s expert loop had exactly this problem. A step loops over the experts its rows were routed to. For each one, the kernel waits for the expert’s weights and runs a path chosen by how many rows the expert serves: a few-row path, with small variants for one to eight rows, and a dequantize-then-multiply path for busier experts. As the batch grows, a step visits more experts, but most of them still serve only one or two rows, so the light path is the one that matters.

One heavy branch slows the light path

The 8-row variant keeps large f32 accumulators that do not fit in the vector registers even on their own. Because it shared one loop body with the one- and two-row variants, the common path spilled registers to memory and loaded them back on every expert: about 0.37 µs per expert, against roughly 1.2 µs to stream that expert’s weights. That overhead had nothing to do with the work the light path itself did.

Two loops instead of one

The fix keeps the heavy code out of the light path’s loop. The kernel sorts a step’s experts by row count and runs two loops: one for experts with at most four rows, and one for the rest. Each loop body now holds only its own variants, so the few-row loop carries 61–64% fewer spill instructions. Every expert still takes the same path as before, so the output is bit-identical.

Schematic. In one shared loop body, every few-row expert is followed by a spill and refill, and the loop falls behind its weight stream. In their own loop, few-row experts keep pace with the weights.Figure 10.

In a kernel test with random routing, decode steps with many requests got 13–19% faster, and the expert loop now keeps pace with its weight stream.

6. Speculative decoding with DFlash2

Without speculation, every output token costs one full pass over the active weights. [21] drafts a whole block of tokens in one forward pass of a small model; we use Muse Spark’s DFlash2 draft model.DFlash

One speculative step. The draft model reads hidden states captured from the full model. The token strip is an illustration.Figure 11.

The draft attends bidirectionally within its block and proposes all of the block’s tokens at once. The full model checks the whole block in one megakernel step and keeps the longest prefix of drafts that matches its own choices, plus one token of its own.

This suits TPU well: MXU time grows with the number of row and output tiles, not with multiply-adds, and a block’s few rows fit in the same row tile as one token, so verifying a block costs little more than verifying one token. Measured on GSM8K with real acceptance, DFlash2 cut the megakernel’s time per output token for a single request from 3.93 to 1.95 ms, 2.0×.

7. More context per device: KV layout and L2 HiCache

On agent traffic, KV capacity is throughput: every prefix that falls out of the cache comes back as a 100K-token re-prefill. After the weights, each device has only about 20 GiB left for KV, split between a full-attention pool for the 16 global layers and a sliding-window pool for the other 46.

fp8 KV in a sequence-on-lane layout

Each device holds 2 of the 16 KV heads, each 64 values wide: half of a vector register’s 128 lanes. A token-major cache packs a head’s K and V side by side to fill the lanes. That works in bf16, but fp8 [22] packs four values per 32-bit word down the sublanes, so a K-and-V pair is padded to four slots and switching to fp8 alone saves nothing.

The sequence-on-lane layout puts a page’s tokens along the 128 lanes and the head dimension down the sublanes, so each word holds four fp8 values of one token and nothing is padded. It halves both the KV memory and the KV bytes each step reads. Google engineers added this layout to SGLang-TorchTPU’s ragged paged attention kernel (), which serves prefill here, and the describes it for Qwen 3.5. We rewrote the megakernel’s attention reads and its KV writes for it.#344TorchTPU post

The draft model’s KV in the sliding-window pool

The draft model only attends to the last 2,048 tokens, but the server allocated its KV for the full context, almost a third of all KV memory per cached token. Serving it from the sliding-window pool lets the same HBM hold 38% more tokens.

L2 HiCache on TPU

We enabled SGLang’s hierarchical cache (HiCache) [23] on TPU, with host DRAM as an L2 behind every HBM pool: full-attention, sliding-window and draft. When HBM evicts a session’s prefix during a tool pause, its pages stay in host memory and are copied back on the next turn instead of being recomputed, as in multi-turn KV caching systems such as CachedAttention [24]. Making it work alongside speculative decoding and the overlap scheduler needed a new synchronization fence. On agent traffic, the L2 cache raised throughput by up to 77%.

Session-aware eviction

Agent traffic brought a second problem: the cache did not know which old prefixes would be needed again. An agent session is a tree of conversations: a main agent can sit idle for a quarter of an hour while its sub-agents run, then come back with its whole context. To plain LRU eviction, that idle conversation looks like the coldest data in the cache, so it goes first, and its next turn recomputes a long prefix.
