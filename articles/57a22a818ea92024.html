chat.nvim v1.12.0 在 2026-11-15 打上 tag。release notes 里 28 条 feat、35 条 fix，飞书和 Telegram 从单文件拆成了模块目录，Discord 这一版也补齐了同形状的子模块。

这一版新加的东西主要在三个方向：缓存和上下文从「心里有数」变成「屏幕上看得见、配置里调得动」；用量单独记一份账，能按小时看；飞书从「能收发消息」做到「能按人管权限、能私聊、每人一个工作目录」。下面按功能逐项写，配置名和默认行为都带上。

一、缓存探针：第一次看到前缀断在哪

缓存能不能命中，取决于请求前缀是否逐字节相同：system prompt、tools 数组、已经发出的消息。差一个字节，从那一位往后全部按原价计费。

这个道理早就知道，但我一直没有工具去确认每次请求到底断在哪。v1.12 新加 lua/chat/sessions/cache_probe.lua，给每个请求打指纹，跟同会话的上一次请求比，断点位置和原因都写进日志。

指纹只取字符串前 4096 字节，并把长度也混进哈希：

local SAMPLE_BYTES = 4096

local function hash_string(s)
  if type(s) ~= 'string' then
    return '0'
  end
  local n = #s
  local h = 2166136261
  local limit = n < SAMPLE_BYTES and n or SAMPLE_BYTES
  for i = 1, limit do
    h = (h * 31 + s:byte(i)) % 4294967296
  end
  h = (h * 31 + n) % 4294967296
  return tostring(h)
end

工具输出动辄几千行，全量哈希没必要。只取头部再混入长度，一个被截断的长字符串就不会冒充短字符串。这块是脏活，够用就行。

挂点三个，每个都是 best-effort，探针自己出错不能拖垮请求：protocol.request 调 begin_request，tools.request_tools 调 record_tools，progress.set_progress_usage 调 record_usage。

日志分两类。健康的那种长这样：

[cache] session=2026-11-15-09-14-22 req=#12 append +3 messages, prefix intact (45)

断了的长这样：

[cache] session=... req=#13 break=#7/46 reason=tools (messages before the break stay cached)

词表一共五个：append、system、tools、messages、truncated。断点之前的消息还在缓存里，只有后面那段重新计费，所以日志把 break=#7/46 这个位置单独标出来，方便判断损失有多大。

第一次跑出 reason=tools 的时候我盯着看了半分钟，因为那一回合我根本没碰工具配置。

二、chat.usage：把三种 provider 的用量压成一张表

探针能定位断点，但缓存命中有没有变好，还得看数字。这一版顺手把用量解析收拢成一个模块 lua/chat/usage.lua。

起因是很久以前某个会话里缓存那一栏永远是 0%。我一开始以为 DeepSeek 压根不返回这个数字，翻文档才发现它返回了，只是字段名跟 OpenAI 不一样。把三家摊开对比：

provider 字段
OpenAI / DashScope usage.prompt_tokens_details.cached_tokens
DeepSeek usage.prompt_cache_hit_tokens
Anthropic usage.cache_read_input_tokens

渲染那边原来只认第一种，chat.usage 做的就是把任意 provider 的 payload 压成同一张表 { total, prompt, completion, cached }，另外带 hit_ratio、summary、sum 三个派生值。取不到的字段返回 0 而不是 nil，调用方不用到处写 or 0。

模块里那段注释我写得很直白，因为下次改的人大概率还是会想加分支：

Every provider reports usage with its own shape, so the UI kept
re-implementing "which field holds the cached tokens" in several places and
got it wrong in most of them (only the OpenAI `prompt_tokens_details` shape
was understood, so DeepSeek and Anthropic cache hits always displayed 0%).

三、slide_step：上下文窗口按批推进

截断窗口以前每回合都往前挪一格。keep_recent 是固定的，但起点取 #messages - keep_recent，消息一多，起点每条都动，前缀跟着断，只是断点靠后一点，日志里 reason=messages 一路刷。

新配置 slide_step 把起点按批推进：

local raw_cutoff = #other_messages - config.keep_recent
local cutoff_idx = raw_cutoff
local step = tonumber(config.slide_step) or 0
if step > 1 then
  cutoff_idx = math.floor(raw_cutoff / step) * step
  if cutoff_idx < 1 then
    return messages, false
  end
end

窗口在 keep_recent 和 keep_recent + slide_step 之间来回震荡，攒够一个 step 才往前跳一次，跳一次断一次，中间那些回合前缀完全一致。默认 slide_step = 1，也就是保持旧行为；我这边的会话设成 10。

代价有两个：窗口会略微超出预算，截断的时机晚于 trigger_threshold。都认了。

四、窗口提示固定在数组末尾

截断之后要插一条提示，告诉模型「早期消息被裁掉了，需要历史可以调 get_history」。位置我以前选在最新一条 user 消息之前，看起来最自然。

问题是这条提示的内容里带着每次请求都会变的数字：总消息数、当前窗口的起止。它只要落在数组头部，第一个字节就变了，整个前缀作废。而截断后只剩一条 user 消息的单轮窗口，它必然落在头部。结果是每请求断一次，只剩 tools 数组还在缓存里。

现在它固定是最后一条。代码注释里我把这段写得很长，因为下次再有人想把它挪回去，得先看完。

lazy tool loading 按需加载工具，每个回合重新算一遍要发哪些。工具是「用到了才加」，顺序自然跟着调用顺序走。system prompt 一样的会话，tools 数组顺序不同，后面全不匹配。

1.12 把顺序冻成 append-only：

tools.essential → 本回合第一次出现的懒加载工具 → find_tool 永远最后

已经在数组里的工具再调用、再被 find_tool 激活，都不动位置，只有真正新出现的工具追加一格。

配套改了 find_tool 的返回值。以前它会回显工具的完整 schema，现在只回一句 Enabled tool "git_log".，schema 靠下一次请求的 tools 列表生效。省下的 token 不算多，但它确实让返回值变成了几行字。

六、用量账本：写到盘上，按时段查

探针和命中率是给人看的，账单是给月底看的。这版把用量单独记一份，lua/chat/usage_stats.lua，落盘在 {storage_dir}/usage_stats.json。

结构三层，record shape 完全一致：

层 键 保留
total 无 永久，不清理
hourly YYYY-MM-DDTHH 7 天
daily YYYY-MM-DD 365 天

键用定宽 ISO 字符串，字典序就是时间序，清理的时候直接拿字符串比大小，不用解析成时间。清理是懒的，record() 里顺手 vacuum，闲置的机器就把旧 bucket 留在盘上，直到下一次请求。

查询有 total() 和 range(since)。跨度小于 48 小时合并 hourly 桶，更长合并 daily 桶。窗口起点所在的那个桶整块计入，所以查询结果最多超出一个桶。这个精度问题我没有修，hourly 桶本来就是拿来看趋势的，多一小时不影响判断今天是不是烧超了。

HTTP 侧开了两个新端点，GET /usage-stats 和 DELETE /usage-stats。401 现在带 JSON body，客户端不用只靠状态码猜是 key 错了还是路径错了。

七、药丸式窗口标题

UI 上做了个改版，结果窗口和输入窗口的标题都换成药丸排版，中间用窗口自己的边框字符连起来，看上去像是嵌在边框里而不是浮在上面。结果窗口那三颗是：

╭ opus | sonnet ╮───╭ 128.4K (96.2K↑/32.2K↓) ╮───╭ 💾 74% ╮
会话标题（跑请求时带 spinner 帧）、累计 token 和 prompt/completion 拆分、缓存命中率。没用量的时候只显示第一颗。输入窗口那三颗是 provider model、cwd、绑定的集成。

写这段的时候遇到一个小问题：title.build 当初是按 varargs 设计的，可选的药丸传 nil 就行。我中途改成传 table，带洞的数组在 ipairs 下会静默丢掉第一个空位之后的全部内容，屏幕上只剩一颗药丸，还不报错。改回去了，注释里补了一句为什么不换。

八、飞书：ACL、私聊容器、card 回复

这一块跟缓存没关系，是攒下来的功能需求。

lark.lua 原来是一个文件，加了权限和私聊之后放不下，拆成 lark/{acl,container,poll,send,state,identity,p2p,url,http}.lua，外面留一层 facade。Telegram 这版一起拆了，形状一样。因为一个 bot 服务多个会话的时候，游标、会话、准入策略都得按会话各存一份。

权限三档 allow_all / whitelist / blacklist，加一组 admins。admins 里的 open_id、邮箱、手机号都行，邮箱和手机号在 connect 时解析一次然后缓存，open_id 不花 API 调用。

配置里的白名单和运行时白名单是两层，合并而不是覆盖，运行时优先。这样 :Chat bridge 之后管理员能在群里直接 /allow @someone、/deny @someone，改动当场写进 lark.json，重启不用改配置。

私聊（P2P）默认拒绝。allow_all 说的是「绑定的那个群」，不代表谁都能开 DM。要私聊得单独配 p2p.allow。

每个私聊一个独立工作目录，<cwd_root>/lark-<chat_id>。两个人在私聊里同时让 bot 改文件，共用一个 cwd 会互相踩，而且他们不该看到对方的工作区。

poll 那边修的都是重启和异常路径：

  • 启动时把消息游标重置成 now。不清的话重启一次就把历史消息从头再处理一遍，群里会出现 bot 突然回复几个小时前的话
  • tenant token 拿不到时整批丢弃，不逐条重试。逐条重试会让同一条消息被处理好几轮
  • 已处理消息 id 的缓存只留最新的一批，内存有上界
  • 发送在 token 解析窗口内串行化，否则并发 send 会拿着旧 token 打出去
  • 断线时要主动中断当前 poll 链并清掉 timer。有一条缺陷是这样的：disconnect 之后 poll 链还在跑，下一轮拿到空 token 又自己重连

回复从纯文本改成 interactive card，Markdown 有了渲染的地方。

九、Discord 和 Telegram 对齐

两边这一版补了同样的两件事：准入和私聊容器。

Discord 加了 /allow、/deny、/acl，还支持把整个 guild 的文本频道一次性注册进来，每个频道各自一个游标和一个会话；私聊按 peer 分配工作区。Telegram 启动时会跳过积压的 update，不然重开 Neovim 会一次性把离线期间的群消息全处理一遍。

十、零碎

find_tool 的 query 现在收数组，一次能激活好几个工具，省一个往返。不记得名字可以打缩写，gcm 会解析到 git_commit，规则是「查询字符按顺序出现在工具名里」，只在精确匹配和子串匹配都落空、且查询长度 ≥ 3 时启用。

bitable 加了 create_field / update_field / delete_field 三个新动作。飞书改字段名也要求把 type 一起传回去，所以 list_fields 的输出里 field name 和 id 都给了，模型直接抄。

fetch_web 修了两处。一是 loopback 地址不再走 proxy，本机跑着 HTTP server 却因为环境变量里的 http_proxy 连不上，这个坑我自己踩过一次。二是响应体里的非 UTF-8 字节会被清掉，不然上游 API 直接回 NonUTF8Body。

会话层三个修复：reasoning_content 不再往请求里重发（多数 provider 不接受自己之前吐的思考内容）；首开 :Chat 会进上一次的旧会话，现在建新的；会话被 HTTP 那边删掉时，TUI 会切回上一个会话而不是留在一个空窗口。

升级

lazy.nvim 直接拉最新 tag 就行。

需要留意的有三件：

  1. usage_stats.json 是新文件，不想记录就设 usage_stats = { enable = false }
  2. tools 数组的顺序和 find_tool 的返回值都变了。如果你的 skill 或者外部脚本 grep 了 find_tool 的旧输出文本，会 grep 不到
  3. 飞书多了 acl 和 p2p 两节配置，不配就还是 allow_all，行为跟以前一样
