Correctness and debugging

TitanRL comes with strong correctness guarantees! Say you just enabled a new algorithm or kernel, launched a run, and the rewards differ from your baseline. Is that your change, or noise? Batch-invariant mode takes one source of noise off the table: in supported on-policy configurations, the trainer and generator produce bitwise identical log probabilities, so the gap between them is exactly zero at every step. FlexShard

TorchTitan leverages FSDP2 for row-wise or column-wise sharding model state (parameters, gradients, and optimizer). However, newer features such as distributed Muon optimizer and blockwise quantization of parameters warrant or benefit from more esoteric sharding policies that are not possible with FSDP2. To address this, TorchTitan now integrates with – a new data parallelism library for sharding model and optimizer state. FlexShard offers a bucket-centric API where each bucket of parameters can be sharded according to a customized policy and has an optimized runtime that overlaps bucketed communication with computation. FlexShard offers similar placements as FSDP1 and FSDP2, but additionally offers new placements such as where one rank owns an entire parameter, and that allows 2D tile-aligned sharding.FlexShardPlacementOwnedBlockShard

FlexShard has enabled TorchTitan to support the distributed Muon optimizer in an efficient way where parameters optimized using Muon are sharded using and placements – eliminating the need for All Gather collectives before performing the optimizer update. On DeepSeekV3 at 256 H100s, this improves the Optimizer time duration by up to 79% compared to an equivalent FSDP-only implementation.OwnedBlockShard

FlexShard also enabled TorchTitan to support blockwise-quantized parameter AllGathers: where FP8-quantized parameters are gathered by the collective, reducing communication volume by ~50%. With FSDP2, since the sharding boundaries may not necessarily be aligned with the blockwise quantization boundaries – we were forced to either gather the parameters in BF16 – increasing communication volume, or perform the FP8 all-gathers but with additional collectives for the quantization scaling factors. FlexShard’s placement enables TorchTitan to get the best of both worlds – gather the quantized parameters without any additional communication for scaling factors, as the sharding strategy is by-definition aligned with the quantization scheme: on LLama3 405B at 256 H100s, this improves end-to-end training step time by up to 20%.BlockShard

Distributed infrastructure

TorchTitan serves as an important validation stage for new communications features as they ship in PyTorch. Large-scale training stresses every part of the communication stack (initialization, collectives, failure handling and memory registration), which makes TorchTitan a demanding testing ground.

In , the NCCL implementation from torchcomms was ported into c10d as a new, opt-in NCCL backend. This allows us to enable new features much faster. It is designed as a drop-in replacement for the existing one and registers under the standard backend name.   • Raw access to NCCL shrink/grow and suspend/resume APIs

Symmetric memory continues to be an important performance lever for TorchTitan. TorchTitan’s MoE layers can now run on Dist-MoE, a newly open-sourced distributed Mixture-of-Experts library, with ready-to-use DeepSeek V3 recipes for NVIDIA Blackwell GPUs. Dist-MoE moves tokens between experts over symmetric memory and fuses that communication with expert compute. FSDP in TorchTitan can also allocate its communication buffers from a symmetric memory pool. Checkpointing

TorchTitan has integrated support for a new distributed checkpoint library, . This new library removes per-save synchronization in the default (DCPv1) saves. We do one collective (on the default process group) before the first save to share metadata; after the first save, we do no collectives.torch_checkpointingtorch.distributed.checkpointing

As pretraining grows past 16k ranks, the previous approach of using GLOO collectives to achieve synchronizations scales poorly with the number of nodes. torch_checkpointing’s approach of only running a lightweight barrier per save wins out at these scales.

We also improved upon other things within DCPv1, such as saving the whole checkpoint item (e.g. model, optimizer, etc.) in at once rather than calling on each individual tensor, and making custom components pluggable (e.g. writing a custom storage backend optimized for your infra).torch.savetorch.save
