开发AI · · 今天 LiesAuer 这个问题实际上牵扯到多个工具，不确定根源是否在于 Codex 的机制问题，但本文不做过多追溯。事实上，Codex 官方仓库堆积着好多个关于工具调用失败的 issue，但貌似和这个问题不太一样，就不贴出来了。 起因是我两台电脑中一台电脑的环境是正常运行rg.exe的，但是另一台呢就不行，一直报错，导致 Codex 一直回退到使用 powershell 以及 python 去用无比恶心的命令去翻东西，特别是涉及到转义的话，十有九错。他们都是通过 winget 直接安装的，就是不知道为啥另一个不行，然后我通过直接问 AI 失败的原因，给的回复是： ``` Codex 的 PowerShell 会话把 rg 解析到了 WinGet 的路径 C:\Users\xxxxx\AppData\Local\Microsoft\WinGet\Links\rg.exe。它是一个指向 WinGet 包目录的符号链接，但当前工具环境无法访问链接目标；因此启动时报错。 ``` 然后通过对比两台电脑调用 rg.exe 的位置，确实是发现不一样，调用失败的是位于额外的 Links 目录下的快捷方式，另一个正常的调用则是直接指向本体。 ``` where.exe rg.exe C:\Users\xxxxx\AppData\Local\Microsoft\WinGet\Links\rg.exe where.exe rg.exe C:\Users\xxxxx\AppData\Local\Microsoft\WinGet\Packages\BurntSushi.ripgrep.MSVC_Microsoft.Winget.Sourceyb3d8bbwe\ripgrep-15.2.0-x86_64-pc-windows-msvc\rg.exe ``` 我不确定为啥同样的 winget，一个会创建链接，一个不会，但不过多深究了，既然问题确定了，那直接简单粗暴的把`C:\Users\xxxxx\AppData\Local\Microsoft\WinGet\Links`下的`rg.exe`删了，同时把`C:\Users\xxxxx\AppData\Local\Microsoft\WinGet\Packages\BurntSushi.ripgrep.MSVC_Microsoft.Winget.Sourceyb3d8bbwe\ripgrep-15.2.0-x86_64-pc-windows-msvc`补到环境变量中，然后重启 Codex 即可。 Codexrgrg.exeripgrep
