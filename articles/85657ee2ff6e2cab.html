出品｜虎嗅黄青春频道

作者｜商业消费主笔 黄青春

题图｜虎嗅拍摄


虎嗅独家获悉，腾讯即将发布一款面向 C 端用户的 AI 搜索引擎，界面极简、全面 AI 化，强化权威信源排序，会将 AI 问答与网页搜索揉在同一体验里。而就在两周前，腾讯云已针对 B 端客户发布“元宝搜索”（前身为联网搜索），其在内部业务低调运行数年，如今扛着 AI 搜索重担被推到了聚光灯下。


据腾讯内部人士向虎嗅透露，这款 C 端搜索引擎与元宝 APP 内置搜索、腾讯云“元宝搜索”API 共享同一套底层能力，即在面向浏览器与网页搜索场景时，三者本质是同一套能力在不同入口下的产品化呈现。


目前，元宝搜索提供 Skill、MCP 和 API 三种接入方式，凭邀请码限时在10月、11月最高可调用 6000 次；接入流程也简单：在腾讯云拿到 API Key，打开终端敲一条 curl 命令即可发起请求。



这不免让人好奇：腾讯在搜索赛道深耕十余年，为什么偏偏等到现在才把这套能力升级成云服务对外卖？


很大程度上源于，百度稳坐国内搜索头把交椅已超二十年；腾讯兜兜转转十余年，做过 SOSO、收购搜狗、上线微信搜一搜、再到元宝 APP，始终没在 C 端撕开实质性缺口。眼下，腾讯借 Agent 爆发的东风，自然会对 B 端搜索基础设施摩拳擦掌。


据虎嗅了解，元宝搜索团队 2024 年年中与元宝 APP 同步组建，整合了 QQ 浏览器、搜狗搜索的核心技术基因，把腾讯十余年的搜索算法积累与工程经验，重构为一套面向 AI 时代的搜索基础设施。


在此之前，这套能力只服务于 QQ 浏览器和搜狗：前者曾长期是超级流量入口，后者稳居第二梯队，体量不容小觑；如今 Agent 赛道爆发，搜索正从面向 C 端的产品入口，下沉为所有 AI 应用的底层能力，标准化搜索 API 的需求快速扩容。


基于此，腾讯不再满足于只服务内部业务和存量客户，顺势将元宝搜索升级为云服务对外变现。从这个角度看，元宝搜索的开放，与其说是战略新局，不如说是看见赛道热度后，把现成技术资产快速推向市场的务实之举。


腾讯首次公开内部AI搜索机制


腾讯云副总裁、元宝搜索研发负责人马晋把搜索划分为三个时代：1.0 是人输关键词、人筛结果；2.0 是大模型读结果、生成答案；3.0 是 Agent 拆解子问题、搜索返回结构化结果支撑推理。


具体而言，搜索 1.0 是关键词时代，舞台中央是百度和谷歌。腾讯折腾了十余年，做 SOSO、全资收购搜狗，始终没能在 PC 与移动市场坐稳 TOP 阵营。


到搜索 2.0 的大模型时代，百度推出文心一言、字节推出豆包、OpenAI 上线带联网功能的 ChatGPT，大模型与搜索深度融合成为主流。腾讯推出元宝 APP 应战，将大模型和搜索能力绑在一起，但元宝始终定位为 C 端 AI 助手，即便长成 MAU 过亿的 Chatbot，与豆包的 MAU 仍有差距，没能在搜索赛道建立起足够话语权。


大步迈入搜索 3.0 的 Agent 时代，腾讯不再执着于硬刚 C 端入口，转而将 AI 搜索押注在 B 端基础设施赛道。腾讯公布了一组元宝搜索的运营数据：数千亿级索引规模，覆盖 13 个垂直行业、157 个权威信源，全网覆盖率 96%；已全面支撑 WorkBuddy、ima、腾讯金融科技、腾讯视频等 50 余个内部核心业务，日均调用数亿次。




马晋从认知、算法、架构、内容四个维度，向虎嗅拆解了元宝搜索的技术升级路径。


先看最直观的规模数据。官方公布的索引指标为：日增 50 亿网页、可检索文档 500 亿、向量索引超 1500 亿，这一规模在行业里不算最大；但中文索引覆盖率做到 95%，重点垂直领域接近 100%，意味着元宝搜索没有盲目追规模，而是将权重压在优质内容和垂直领域的收录上。


再看被反复强调的 157 个权威信源，合作方覆盖携程、美团、京东、大众点评、汽车之家等头部平台。其实这个点有点虚，因为这类商务合作不具备排他性，元宝搜索今天能拿到的合同，别家明天也能靠商务谈判拿到。


真正值得拿出来说的是自有内容：元宝搜索已接入腾讯视频、腾讯医典、腾讯自选股，未来不排除进一步打通微信生态——这才是其他家望而却步的价值所在。


更关键的是，马晋在回应“打不开的网页如何处理”时坦言：“如果网站设了反爬就不收录，这是尊重对方的知识产权。”换言之，真正高价值、设置反爬机制的内容，元宝搜索同样无法通过通用检索获取，只能逐家洽谈合作。


所以，掰开元宝搜索的核心技术逻辑仍是数据飞轮+ Agent 协同+ Trace Debug。马晋将其形容成“用 AI 去找 AI、用 AI 去升级搜索”，本质是让大模型辅助搜索数据的标注、清洗与迭代，这是全行业的标配方向，几乎所有头部搜索团队都在做，并非腾讯独有的技术差异化。


虎嗅与两位技术专家沟通发现，元宝搜索算法升级采用三阶段训练范式：Label Agent 标注、Teacher Model 学习、Student Model 蒸馏。这套流程是大模型排序领域的标准蒸馏流水线，在学界和工业界已落地两年有余，业界共识蒸馏的真正壁垒在 Teacher Model 的基底质量、标注数据的规模厚度，以及 Student Model 在精度与延迟之间的平衡，而这些决定效果的细节，元宝搜索发布时并未给出具体佐证。


据虎嗅了解，腾讯搜索实际用 Gist 技术省下的成本超过 30%，原理是把文档的 gist token KV Cache 缓存下来，不同 query 召回同一文档时直接复用；即便 query 长尾分布，召回排序后的文档仍有聚集效应——在元宝搜索的混合排序场景里，文档命中率约 85%，节省相当可观。


不过，这一效果高度依赖缓存命中率，网页无法全量存储，只有热门页会被缓存，长尾页仍需实时算。官方没公布具体命中率，而搜索请求天然符合长尾分布——这意味着真实平均成本节约，大概率低于 30% 的理论上限。


此外，官方公布的召回率、覆盖率、延迟、满意度等关键指标，全部来自腾讯内部评测，缺乏公开 Benchmark 与可复现测试集。以响应速度为例，官方称升级后核心链路响应时间压到 300ms 以内（此前约 400–500ms）。


虎嗅认为，Agent 多轮调用场景下延迟会被成倍放大，把单次耗时压下来，是终端体验的关键。从实测看，真实网络环境下连续 5 次调用延迟在 345–485ms 之间波动（平均约 420ms），峰值与最低值相差 60%——要知道，对支撑高并发 Agent 的基础设施而言，延迟波动的危害远大于平均延迟；至于跨地域、突发流量等极端生产场景的表现，目前尚无任何公开数据。


即便，对复杂检索基座而言上述成绩已具备可用性，但对追求极致稳定的企业级客户，如何抹平长尾延迟、扛住极端流量，是元宝搜索接下来必须向市场证明的下一道难题。


也就是说，腾讯云闷头憋的元宝搜索，本质是把传统搜索时代沉淀的成熟管线，用大模型思维重做了一遍底层，并在腾讯内部真实业务里完成验证。据虎嗅了解，已有多家头部大模型公司和外部企业接入，但在问及具体名单时，元宝搜索团队以“涉密”为由拒绝透露。


好在马晋回应“无法回避的技术瓶颈”时说了一句实话：“其实就是 Trade-off 的过程……这更多是内容、算力、耗时和成本之间的平衡。”这句话恰恰点破了行业现状：搜索发展至今，早已没有独门秘籍，比拼的是工程执行、成本控制与信源资源。


这次枪口瞄准了谁？


再将视线拉回搜索 3.0 时代，行业正分化出两条清晰路线：


一条是模型与搜索绑定的一体化路线，代表玩家是 OpenAI、Google、百度、字节，强调搜索是大模型的核心能力之一，二者深度绑定、协同优化，客户选定一家大模型就能直接用配套搜索，无需额外对接，其接入成本低、体验一致，更适配中小客户和一体化场景。


另一条是独立中立的搜索服务路线，腾讯元宝搜索坐这桌，核心逻辑是：未来 Agent 市场必然高度碎片化，模型、框架、场景五花八门，客户需要中立、灵活、不被绑定的搜索底座。这条路更适合有技术能力、有定制需求、重视数据主权的中大型客户。


从目前的行业格局看，绑定路线暂时占上风，因为多数开发者和企业更倾向一站式方案，不愿额外花钱对接独立搜索、调试链路；但 Agent 生态仍处于早期阶段，最终市场走向谁也说不准。


有鉴于此，元宝搜索主打中立开放，确实为不想被单一厂商绑定的客户提供了新选择（比如自有大模型企业、需兼容多模型的开发者、对数据主权要求高的政企与金融机构），客户可自由搭配任何厂商的大模型，只把搜索环节交给元宝搜索，避免技术栈被锁死。


况且，腾讯云本身手握大量政企、金融、互联网、教育行业客户，过去他们采购云服务时若需要搜索能力，可能得单独对接百度；如今腾讯顺势将搜索 API 直接打包进云服务套餐，这无疑会对百度的企业级搜索业务带来直接冲击。


尤其在政企与金融领域，客户对服务商的综合能力与合规能力要求极高，腾讯云把搜索能力融进既有云体系，客户的迁移成本和决策成本都会低很多。


当然，OpenAI、Google、百度、字节的优势在全网通用搜索的广度，垂类深度合作并未形成壁垒；腾讯原本可借自身生态快速在垂类场景切出差异化；但以元宝搜索目前的状态，尚无法对百度形成实质威胁。因为其在产品能力、服务体系、客户定位三方面都存在缺口：


第一，不支持多跳搜索。目前只提供原子化接口，多跳能力未来或基于 WorkBuddy 沉淀的 Agent 能力逐步开放——这意味着客户买完搜索底座，还得自己搭一层 Agent 才能做多跳推理，那宣传的“开箱即用”就要打个折扣。


第二，调用元宝搜索目前只能拿到标题、摘要、链接和垂类卡片；要提取网页正文，客户还得自己再对接一遍。等于说，完整链路本应是搜索结果获取 → 网页正文提取 → 信息加工，现在只开放了第一步，剩下两步客户自己补，接入成本被悄悄抬高了。


第三，面对设了反爬的网站，元宝搜索选择不收录，这在合规上无可指摘，却也意味着大量高价值内容处在索引盲区；时效性内容只能做到一小时一更新，真正的实时获取依赖尚未开放的 Fetch 接口，对实时性要求高的场景，目前能力远远不够。


腾讯相关负责人也坦言，目前第一大客户仍是腾讯内部产品，这符合腾讯一贯的“狗粮自吃”风格，即内部说好，再顺势对外。


问题在于，内部业务可以定制化适配，团队同属一家公司，出问题拉个群就解决，资源可按需倾斜；但外部客户拿到的是标准化 API，出了问题是否只能走工单流程排队等响应？何况，对外服务还要兼容不同模型、不同 Agent 框架、不同业务场景，并承担 SLA 承诺，这中间的鸿沟远不止开放一个 API 就能填平。


对此，腾讯云回应虎嗅，目前需求井喷，相比成熟的标准化云 API，大模型搜索 API 仍有大量差异化需求要消化；团队在持续迭代产品的同时，针对部分客户的差异化需求会 1V1 处理。


更严峻的考验还在商业化：从内部工具变成对外商品，除了技术，还有一整套服务体系要补，SLA 怎么签？故障赔付怎么定？数据合规与隔离怎么做？政企私有化部署如何落地？计费粒度是否够灵活？


对此，虎嗅问询了元宝搜索商业化团队，对方表示这部分已有相对成熟的方案，不少车企与国内知名大模型厂商已开展深度合作。


别人愿意来撑场子可能碍于长期商业合作，但一个 ToB 基础设施的成色，终究要靠高峰期不宕机、故障有响应、扩容能承接来证明，而这些都需要真实外部客户与时间来打磨。


腾讯官方列出的目标客户有四类：大模型公司、智能车企、办公场景、教育行业。以智能车企为例，搜索高度聚焦导航、天气、POI 等垂类场景，元宝搜索被整合进腾讯智慧出行面向车企的方案，嵌入 AI 座舱，这是当下车企需求最旺的服务，因为车载场景对搜索结果可信度要求极高。至于办公、教育行业的头部客户，要么已与百度等厂商绑定，要么倾向自建，中小客户则对价格高度敏感。


综上，元宝搜索有扎实的技术底子和清晰的差异化方向，拉开了 B 端搜索基础设施竞争的序幕；但它此次全面开放，一头扎进的却是竞争白热化的红海——当前 AI 检索 API 市场价格战早已刺刀见红，元宝搜索再去贴身肉搏，无疑是一场硬仗。
