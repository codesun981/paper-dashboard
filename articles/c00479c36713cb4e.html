今天闲的没事，部署了一套 artex ，然后接入 ds 让它探测我在自己的 home lab 上部署的公网服务有没有漏洞。

本来是只想让它测测主域名入口的，结果它直接就发现了同 IP 存在复数个二级域名，然后就开始了无情的大调查。

目前已经探测了 37%的链路，1 个 critical ，6 个 high 的漏洞。高危的我都实时快速修复的修复，下线的下线。几个危险入口已经处理了，后面估计没啥大问题了。

总结起来几个严重的问题，从低到高：

  1. 我几年前部署的 cAdvisor 服务意外将端口暴露在防火墙之外了，估计当时是远程调试了一下，结果忘记关了。可以在公网请求获取到我所有 docker 服务的元信息。不过我都是内网服务，暴露切面不多，这个只是信息泄露。

  2. 抓到了 minio 中一个可以公开访问的桶，拿到了全部的数据。好巧不巧，这个桶是放的我之前自己开发的 AI 网关旧版使用的所有请求日志记录。aetex 从一堆 AI 的请求中，发现了包含的一段配置文件内容，其中恰好有一个 minio 的一个高权限的调试 key/secret 。然后整个 minio 就沦陷了。

  3. 在上一步拿到的配置文件里面还有 redis 和 postgres 配置。redis 可以直接写入 refresh_token ，从而绕过登录让伪造的 refresh_token 可以通过鉴权。postgres 可以通过超级用户 PROGRAM 迂回执行命令，直接拿下当前的 docker 部署的 postgres 容器，并可以作为跳板进一步尝试逃逸。不过还好这些攻击都必须在内网进行，因为 artex 部署在本机才能实现。

  4. 我有一个 hoppscotch 的服务，自部署的 web 可用的类 postman 服务。它需要通过浏览器插件或者一个额外的代理服务 proxyscotch 来实现浏览器中跨域访问各类接口。这个 proxyscotch 我没加鉴权，直接构造就可以访问我的内网全部的 http 端点。我看到这个漏洞刷出来的一分钟之内就下掉了这个服务，没让 artex 继续利用到，不然从这个口子继续探测下去，我估计漏洞怕不是要乘 10 。

  5. 我也不知道哪个服务的日志泄露了 SMTP 服务的口令。反正我的企业邮箱可以被直接接管了。这也是我除了 gmail 以外的另一个主邮箱，关联了无数的在线服务。

  6. 通过上面的邮箱找回密码，artex 登录了我的内网 gitea ，里面包含了我的若干未开源项目。以及一个专门用来存储一些重要口令的仓库，其中包含了大量数据库，redis ，甚至阿里云的一个 AK/SK 。至此大部分服务都要沦陷了。
